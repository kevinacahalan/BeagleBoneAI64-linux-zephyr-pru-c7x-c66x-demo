# Yocto Image (`meta-ai64`)

This directory contains a `kas` configuration and the `meta-ai64` layer to build a self-contained Poky image (`ai64-demo-image`) with the entire demo—`ai64`, `ai64-demo`, the four Zephyr R5F images, all fifteen ICSSG images, both DSP images, the `ai64_la` kernel module, and the device-tree overlay—pre-installed. You do not need `beagle-linux/scripts/build.sh` for a Yocto build.

## Layout

- `kas/ai64-poky.yml` — top-level kas config targeting `beaglebone-ai64` / `poky` / `ai64-demo-image`
- `layers/meta-ai64/` — recipes for `ai64`, `ai64-demo`, the overlay, all R5F/ICSSG/DSP firmware, `ai64_la`, kernel patches, `extlinux`, the `sysconf` first-boot service, and USB gadgets
- `sources/`, `downloads/`, `build/`, `sstate-cache/` — generated by `kas-container` (not committed)

## Build

A first build takes roughly **3 hours** on a 16-thread host and needs about **150 GB** of free disk space. From the repository root:

```bash
wget -O kas-container https://raw.githubusercontent.com/siemens/kas/5.5/kas-container
chmod +x kas-container
KAS_BUILD_DIR=yocto/build ./kas-container build yocto/kas/ai64-poky.yml
```

Both `podman` and `docker` work. Set `KAS_CONTAINER_ENGINE=podman` or `KAS_CONTAINER_ENGINE=docker` to choose explicitly (unset, `kas-container` prefers Docker if installed, otherwise Podman). `kas-container build` does not write to an SD card.

## Flash & run

Write the timestamped `.wic.xz` image to a microSD card (verify `/dev/sdX` with `lsblk` first):

```bash
xz -dc yocto/build/deploy-ti/images/beaglebone-ai64/ai64-demo-image-beaglebone-ai64.rootfs-<timestamp>.wic.xz \
  | sudo dd of=/dev/sdX bs=4M conv=fsync status=progress
```

Boot the board and log in as `root` (no password) over the serial console or SSH (`ssh root@<board>`, using DHCP on Ethernet with Dropbear):

```bash
ai64-demo --tmux
```

> [!WARNING]
> This is a development image with passwordless `root` login and everything running as `root` (including the web and MCP servers). Set a root password or keep the board on a trusted bench network.

`ai64` and `ai64-demo` are installed in `/usr/bin`, all firmware in `/lib/firmware`, and `ai64_la` is built into the image.

## How it is built

- **Base layers & machine:** machine (`beaglebone-ai64`), kernel, and layers come from TI's `kas/poky-wrynose-config.yml` (Poky distro). `yocto/layers/meta-ai64/kas/ti-poky-wrynose-config.yml` embeds a copy of that file with its two templates folded in (recording its source commit) so `kas` does not have to clone `oe-layersetup` from `git.ti.com`. `yocto/kas/ai64-poky.yml` layers everything for this demo on top.
- **TI Linux 6.18 kernel & U-Boot 2026.01:** `ai64-poky.yml` sets `TI_PREFERRED_BSP = "ti-6_18"` instead of `meta-beagle`'s default 6.12 kernel, building TI's `linux-ti-staging` (`6.18.51`) and TI's U-Boot `2026.01`. This is a different 6.18 tree than BeagleBoard Debian's—see [Two 6.18 kernels](../docs/kernels.md#two-618-kernels). It already includes the PRU virtio kick (so `pru_rproc` needs no patch) and sends `RP_MBOX_SHUTDOWN` before stopping remote cores (which the Zephyr and DSP images acknowledge).
- **Two kernel patches** in `yocto/layers/meta-ai64/recipes-kernel/linux/` make every core cleanly restartable:
  1. Keeps stopped R5F cores powered (matching the Debian `ti_k3_r5_remoteproc` fix; without it, a second `ai64-demo` run fails with `module-reset deassert failed, ret = -19`).
  2. Resets C66x cores after they acknowledge shutdown (a C66x never reports WFI, so without this patch stopping fails with `-ETIMEDOUT`).
- **No `ti-eth-fw-j721e`:** the image omits TI's `ti-eth-fw-j721e`, which `meta-ti` normally installs as `R5F0_0`'s boot firmware for the J721E EVM's main-domain CPSW9G switch. The BeagleBone AI-64's Ethernet port uses the MCU-domain CPSW2G driven directly by Linux (Debian doesn't ship `ti-eth-fw-j721e` either). Left installed, the kernel boots it on `R5F0_0` at startup and it ignores shutdown requests, preventing `ai64-demo` from stopping the core.
- **GitHub mirrors & `git.ti.com`:** `ai64-poky.yml` fetches the kernel, U-Boot, `ti-linux-firmware`, and `core-secdev-k3` from TI's GitHub mirrors (`TexasInstruments/ti-linux-kernel`, `TexasInstruments/ti-u-boot`, etc.) because `git.ti.com` intermittently fails requests. The only remaining `git.ti.com` fetch is the PRU Software Support Package, which TI does not mirror. If that fetch fails, re-run the build, or copy its clone (including its `.done` marker) from another Yocto tree's `downloads/git2/` into `yocto/downloads/git2/`.

## Board verification

On hardware, this TI 6.18 Yocto image completed 20 consecutive `ai64-demo` restarts (15 with copied firmware, 5 from a fresh image build)—stopping and restarting every demo core each run with all cores healthy, the fabric clean, zero kernel errors, and matching PWM, fabric, and DSP timings compared to Debian.
